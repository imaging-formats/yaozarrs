Yaozarrs Guide to OME-Zarr#

What you'll learn

This guide attempts to demystify the OME-Zarr (OME-Zarr) specification and shows you how to work with it using yaozarrs. It is designed to answer common questions and confusions encountered in the community.

Which version is this guide about?

This guide covers OME-Zarr v0.4, v0.5 and v0.6, with tabs to show the differences. The coordinate systems and transformations of v0.6 get their own page: Coordinate Systems & Transformations.

Which version should I write?

It depends on who needs to read your data. Newer versions can express more, but your files are only useful if the tools you (and your collaborators) rely on can read them, so check those first.

What is OME-Zarr?#

The official OME-Zarr specification can be found at https://ngff.openmicroscopy.org/. In case of any discrepancies between this guide and the official spec, the official spec takes precedence!

OME-Zarr is a file format specification used by the bioimaging community for storing multi-dimensional data. It is a "meta-specification", based on the pre-existing Zarr format, which is designed for the storage of chunked, compressed, N-dimensional arrays. OME-Zarr extends Zarr by adding metadata conventions specific to bioimaging, making it easier to store and share complex imaging datasets.

But what is it?

To resolve a somewhat common confusion...

OME-Zarr is "just" Zarr (A file format used in many domains). The "OME" part is a specification on top of the zarr format that additionally defines:

  1. How domain specific metadata should be stored.
    The details are version-specific, but this generally defines the exact form of the data inside of the .zattrs or zarr.json files that accompany the zarr groups.

  2. How datasets are organized.
    Beyond metadata, the OME-Zarr specification also defines how datasets should be organized. For example: it defines how the images collected across a multi-well plate experiment should be organized in a single Zarr directory, or how the different resolutions of a multi-scale (pyramidal) image should be stored.

Working with Images#

An Image is the fundamental building block of OME-Zarr.

As of v0.6 (and since v0.4), a single image may have no less than 2 and no more than 5 dimensions, and may store multiple resolution levels.

  • Spatial dimensions: X, Y, optionally Z
  • Time: T (temporal axis)
  • Channels: C (fluorescence channels, RGB, etc.)
What if I have more than 5 dimensions?

While it is common to have datasets with more than 5 dimensions (e.g., different stage positions in a shared coordinate space, angles in light sheet microscopy, etc.), there is currently no formal specification for more than 5 dimensions in OME-Zarr. You may use the transitional bioformats2raw.layout to store multiple images in a single zarr group. See Working with Collections

If the extra dimension is where each image was taken (stage positions, views from different angles, etc...), v0.6 also lets you describe how the images relate to each other in space with a scene. See Working with Scenes.

See also: an RFC ("request for comments") proposing a relaxation of this restriction: RFC-3

What if I have both RGB and optical channels?

As of v0.6, there is no formal specification for mixing the concepts of RGB image components and conventional "channels" (like optical configurations). You will need to either create a custom group layout or flatten them all into a single channel dimension.

Key difference

Most of the structural changes between v0.4 and v0.5 relate to the transition from Zarr v2 to Zarr v3.

  • <=v0.4: "multiscales" metadata directly in root of .zattrs files
  • >=v0.5: "multiscales" metadata in zarr.json under attributes.ome namespace

Between v0.5 and v0.6, the storage is the same (Zarr v3). The changes are all in the metadata, mostly in how axes and transformations are described (see below).

Axes#

Axes define the dimensions of your image data. Starting with v0.4, axes are objects with a name, and optional type and/or unit (v0.6 adds the optional discrete and longName, and moves axes into named coordinate systems):

Axis Constraints

Constraints for image axes in OME-Zarr are the same in v0.4, v0.5 and v0.6 (in v0.6, they apply to every coordinate system inside a multiscale):

  • MUST have 2-5 dimensions total
  • MUST have 2-3 spatial axes
  • MAY have 0-1 time axis
  • MAY have 0-1 channel axis
  • Ordering enforced: time → channel/custom → space

In practice, this limits valid axis combinations to: [T][C][Z] Y X
(though no explicit restriction is placed on naming conventions)

In v0.6, the axes are no longer listed directly in the multiscale. Instead, they belong to a named coordinate system, and each multiscale lists one or more of these under coordinateSystems. (The why is explained in Coordinate Systems & Transformations.)

Spec JSON:

{
  // found in a "multiscales" object
  "coordinateSystems": [
    {
      "name": "physical",
      "axes": [
        {"name": "c", "type": "channel", "discrete": true},
        {"name": "z", "type": "space", "unit": "micrometer"},
        {"name": "y", "type": "space", "unit": "micrometer"},
        {"name": "x", "type": "space", "unit": "micrometer"}
      ]
    }
  ]
}

yaozarrs Code:

from yaozarrs import v06

physical = v06.CoordinateSystem(
    name="physical",
    axes=[
        v06.ChannelAxis(name="c", discrete=True),
        v06.SpaceAxis(name="z", unit="micrometer"),
        v06.SpaceAxis(name="y", unit="micrometer"),
        v06.SpaceAxis(name="x", unit="micrometer"),
    ],
)

What's new for axes in v0.6

  • discrete (optional): true if the axis may only be indexed by whole numbers (channels usually are), false if values in between samples are meaningful, so interpolating along it makes sense (space and time usually are).
  • longName (optional): a longer name or description of the axis.
  • More suggested types: besides space, time and channel, the spec now lists array, coordinate and displacement (the latter two are used by vector fields). Other strings are still allowed for custom types.
  • Axis names MUST be non-empty, and unique within their coordinate system.

Spec JSON:

{
  // found in a "multiscales" object
  "axes": [
    {"name": "c", "type": "channel"},
    {"name": "z", "type": "space", "unit": "micrometer"},
    {"name": "y", "type": "space", "unit": "micrometer"},
    {"name": "x", "type": "space", "unit": "micrometer"}
  ]
}

Coordinate Transformations#

Starting in v0.4, every dataset MUST include coordinate transformations that map data coordinates to physical coordinates. Coordinate transforms are where you would specify physical units (micrometers, seconds), multi-resolution scales, as well as stage positions and spatial offsets for registration.

Each dataset still has a transformation from its array (pixel) coordinates to physical coordinates, but now it explicitly says where it maps from and to: its input is the dataset's array (by path), and its output is a coordinate system of the multiscale (by name). Every dataset maps into the same coordinate system, which the spec calls the image's "intrinsic" coordinate system.

Scale Transformation:

Spec JSON:

{
  "coordinateSystems": [
    {"name": "physical", "axes": [...]}  // the 4 axes from above
  ],
  "datasets": [{
    "path": "0",
    "coordinateTransformations": [{
      "type": "scale",
      "scale": [1.0, 0.5, 0.1, 0.1],
      "input": {"path": "0"},
      "output": {"name": "physical"}
    }]
  }]
}

yaozarrs Code:

from yaozarrs import v06

dataset = v06.Dataset(
    path="0",
    coordinateTransformations=[
        v06.ScaleTransformation(
            scale=[1.0, 0.5, 0.1, 0.1],
            input={"path": "0"},
            output={"name": "physical"},
        )
    ],
)

Scale + Translation:

A scale and a translation are no longer listed side by side. To add a translation, wrap both in a single sequence transformation (scale first):

Spec JSON:

{
  "path": "0",
  "coordinateTransformations": [{
    "type": "sequence",
    "input": {"path": "0"},
    "output": {"name": "physical"},
    "transformations": [
      {"type": "scale", "scale": [1.0, 0.5, 0.1, 0.1]},
      {"type": "translation", "translation": [0.0, 0.0, 100.0, 200.0]}
    ]
  }]
}

yaozarrs Code:

dataset = v06.Dataset(
    path="0",
    coordinateTransformations=[
        v06.SequenceTransformation(
            input={"path": "0"},
            output={"name": "physical"},
            transformations=[
                v06.ScaleTransformation(scale=[1.0, 0.5, 0.1, 0.1]),
                v06.TranslationTransformation(translation=[0.0, 0.0, 100.0, 200.0]),
            ],
        )
    ],
)

Transformation Rules (v0.6)

  • MUST have exactly one transformation per dataset: a scale, an identity, or a sequence of a scale followed by a translation
  • Its input MUST have a path matching the dataset's path, and should omit name
  • Its output MUST have the name of a coordinate system in coordinateSystems, the same one for every dataset, and should omit path
  • Parameter lengths MUST match the number of axes
  • The scale gives the pixel size in physical units (or the time step). If that isn't known (or doesn't apply) for an axis, the value MUST be the downsampling factor relative to the first level instead (1.0 if that axis isn't downsampled)

Use Multiscale.from_dims

Writing all of this by hand gets tedious. v06.Multiscale.from_dims builds the coordinate system and every level's transformation for you (see DimSpec).

dimension_names are no longer required

v0.5 required dimension_names in each array's zarr.json; v0.6 does not mention them. (yaozarrs still writes them, as other Zarr tools find them useful.)

There's a lot more that v0.6 can express with coordinate systems and transformations (rotations, affines, linking images to their labels or to each other...). See Coordinate Systems & Transformations.

Identical to v0.4, just stored under attributes.ome namespace.

yaozarrs Code (same as v0.4):

from yaozarrs import v05

dataset = v05.Dataset(
    path="0",
    coordinateTransformations=[
        v05.ScaleTransformation(scale=[1.0, 0.5, 0.1, 0.1]),
        v05.TranslationTransformation(translation=[0.0, 0.0, 100.0, 200.0]),
    ],
)

v0.5 Additional Requirement

In v0.5, each array's zarr.json MUST include dimension_names matching the axes:

{
  "dimension_names": ["c", "z", "y", "x"]
}

Scale Transformation (REQUIRED):

Maps array indices to physical coordinates. Scale values represent the physical size per pixel for each dimension.

Spec JSON:

{
  "datasets": [{
    "path": "0",
    "coordinateTransformations": [
      {"type": "scale", "scale": [1.0, 0.5, 0.1, 0.1]}
    ]
  }]
}

yaozarrs Code:

from yaozarrs import v04

dataset = v04.Dataset(
    path="0",
    coordinateTransformations=[v04.ScaleTransformation(scale=[1.0, 0.5, 0.1, 0.1])],
)

Translation Transformation (OPTIONAL):

Adds a spatial offset. Must come after scale.

Spec JSON:

{
  "coordinateTransformations": [
    {"type": "scale", "scale": [1.0, 0.5, 0.1, 0.1]},
    {"type": "translation", "translation": [0.0, 0.0, 100.0, 200.0]}
  ]
}

yaozarrs Code:

dataset = v04.Dataset(
    path="0",
    coordinateTransformations=[
        v04.ScaleTransformation(scale=[1.0, 0.5, 0.1, 0.1]),
        v04.TranslationTransformation(translation=[0.0, 0.0, 100.0, 200.0]),
    ],
)

Transformation Rules

  • MUST have exactly one scale transformation per dataset
  • MAY have at most one translation transformation
  • If translation exists, it MUST come after scale
  • Transformation length MUST match number of axes

Labels (Segmentation Masks)#

Labels are specialized images with integer dtype representing segmentation masks (nuclei, cells, regions of interest, etc.).

They are represented as a special group named "labels/" within an image group.

Careful

This is one of the only places in the specification where the name of the group itself is normative: it MUST be named labels/.

Conforming readers must search for the labels/ group within an image group to discover it: its presence is not indicated in the parent image metadata. (In v0.6, an image may refer to one of its label images, in an optional transformation, but doesn't have to.)

Lining labels up with the image (v0.6)#

By default, a label image's intrinsic coordinate system is "usually understood to be the same" as its image's. In v0.6, you can also link the two when they aren't the same. Say a segmentation tool wrote labels for a crop of the image, with the corner of the crop as its origin. Rather than rewriting the label image's metadata, you can add a transformation to the parent image's multiscale coordinateTransformations, linking its intrinsic coordinate system to the label image's (referenced by name and path, relative to the image group):

{
  // found in the multiscales object of the *image* (not the label image)
  "coordinateTransformations": [
    {
      "type": "translation",
      "translation": [0.0, 100.0, 50.0],
      "input": {"name": "physical", "path": "labels/cells"},
      "output": {"name": "physical"}
    }
  ]
}

Here, a point in the cells label image's physical coordinate system, shifted by (0, 100, 50), gives the matching point in the image's own physical coordinate system. (Either direction is allowed: the image's intrinsic coordinate system may be the input or the output.)

Only simple transformations

A transformation to a label image MUST be an identity, scale, translation, or a sequence of a scale and a translation.

Working with Plates#

A Plate represents multi-well plate data from high-content screening (HCS) experiments. The hierarchy is:

Plate → Rows/Columns → Wells → Fields of View (Images)

Each well can contain multiple fields of view (FOVs) across multiple acquisitions (timepoints).

Directory Structure#

Same as v0.5:

plate.zarr/
├── zarr.json              # contains Plate metadata ("attributes.ome.plate")
├── A/                     # Row A
│   ├── 1/                 # Well A1
│   │   ├── zarr.json      # contains Well metadata ("attributes.ome.well")
│   │   ├── 0/             # Field 0 (Standard multiscales image)
│   │   │   ├── zarr.json  # contains Image metadata ("attributes.ome.multiscales")
│   │   │   ├── 0/         # Full resolution
│   │   │   ├── 1/         # Downsampled
│   │   │   └── labels/    # Optional labels group (see above)
│   │   └── 1/             # Field 1
│   └── 2/                 # Well A2
└── B/                     # Row B
    └── 1/

Three-level hierarchy

Plate Metadata#

The same structure as v0.5, with "version": "0.6" at ome.version.

In yaozarrs, just swap v05 for v06:

from yaozarrs import v06

plate_def = v06.PlateDef(

Working with Collections#

OME-Zarr does not currently have an official specification for collections of images.

By Collections of images, we mean groups of related images, usually sharing a coordinate space, that do not fit into the plate model. Examples include:

  • Multiple stage positions on single coverslip
  • Multiple angles in light sheet microscopy
  • Tomographic tilt series
  • Jagged or otherwise irregular sets of related images that don't fit the multiscales model

Status

There is a long-standing github issue that discusses potential future standards for collections, and RFC-8, which covers this topic (still under review). But as of v0.6, there is no official spec for collections.

v0.6 does add scenes, which cover one common case: images that share a spatial relationship.

The "bioformats2raw" layout is a transitional solution, internally employed by the bioformats2raw tool when dumping multiple series (commonly found in image formats supported by bioformats) into a single zarr hierarchy.

This bioformats2raw layout described in the NGFF spec, is described below:

  3. Otherwise → consecutively numbered groups: 0/, 1/, 2/...

Working with Scenes#

A Scene (v0.6 and later) is a group of images that share a spatial relationship with each other. For example:

  • Tiles of a mosaic, placed side by side in a common "stage" coordinate system
  • The same sample imaged from several angles (e.g. multiview light sheet)
  • Images from different instruments (or modalities), registered onto each other

A scene group has no image data of its own. Its zarr.json holds scene metadata, describing transformations between the coordinate systems of its images, and each image is a normal multiscale image group inside it.

Not sure what a coordinate system is?

Scenes build on the coordinate systems and transformations of v0.6. If those are new to you, start with Coordinate Systems & Transformations, then come back here.

Directory Structure#

mosaic.zarr/
├── zarr.json                  # contains Scene metadata ("attributes.ome.scene")
├── tile_0/                    # a normal multiscale image
│   ├── zarr.json              # contains Image metadata ("attributes.ome.multiscales")
│   ├── 0/                     # Full resolution
│   └── labels/                # Optional labels group
├── tile_1/                    # another multiscale image
│   └── ...
└── coordinateTransformations/ # (optional) transformation parameters stored in Zarr

Scene Metadata#

The scene object MUST contain coordinateTransformations, and MAY contain coordinateSystems of its own. Here, two tiles are placed in a shared stage coordinate system, defined by the scene:

Spec JSON (zarr.json at the scene root):

{
  "zarr_format": 3,
  "node_type": "group",
  "attributes": {
    "ome": {
      "version": "0.6",
      "scene": {
        "coordinateSystems": [
          {
            "name": "stage",
            "axes": [
              {"name": "y", "type": "space", "unit": "micrometer"},
              {"name": "x", "type": "space", "unit": "micrometer"}
            ]
          }
        ],
        "coordinateTransformations": [
          {
            "type": "translation",
            "translation": [0.0, 0.0],
            "input": {"path": "tile_0", "name": "physical"},
            "output": {"name": "stage"}
          },
          {
            "type": "translation",
            "translation": [0.0, 270.0],
            "input": {"path": "tile_1", "name": "physical"},
            "output": {"name": "stage"}
          }
        ]
      }
    }
  }
}

Each input and output refers to a coordinate system by name:

  • With a path, it's a coordinate system of the image at that path (relative to the scene group). Here, physical is the intrinsic coordinate system of each tile.
  • Without a path, it's one of the scene's own coordinateSystems (here, stage).

So these two transformations say "a point in tile_1's physical coordinates, shifted by 270 µm along x, is that point's position on the stage".

yaozarrs Code:

from yaozarrs import v06

stage = v06.CoordinateSystem(
    name="stage",
    axes=[
        v06.SpaceAxis(name="y", unit="micrometer"),
        v06.SpaceAxis(name="x", unit="micrometer"),
    ],
)
scene = v06.Scene(
    scene=v06.SceneDef(
        coordinateSystems=[stage],
        coordinateTransformations=[
            v06.TranslationTransformation(
                translation=[0.0, 270.0 * i],
                input={"path": f"tile_{i}", "name": "physical"},
                output={"name": "stage"},
            )
            for i in range(2)
        ],
    )
)
Writing it (with data)

write_scene writes the scene group and all of its images at once, after checking that the scene and the images fit together:

import numpy as np

from yaozarrs import DimSpec, v06
from yaozarrs.write.v06 import write_scene

# each tile is 600x600 pixels, at 0.5 µm per pixel (300 µm wide)
tile = v06.Image(
    multiscales=[
        v06.Multiscale.from_dims(
            [
                DimSpec(name="y", scale=0.5, unit="micrometer"),
                DimSpec(name="x", scale=0.5, unit="micrometer"),
            ],
            coordinate_system="physical",
        )
    ]
)
data = np.zeros((600, 600), dtype=np.uint16)
write_scene("mosaic.zarr", scene, {"tile_0": (tile, data), "tile_1": (tile, data)})

For bigger scenes (or to write data piece by piece), see SceneBuilder.

Scene rules

  • In a scene, both input and output MUST have a name. A path is required when the coordinate system belongs to an image, and may be left out when it's one of the scene's own.
  • All of the coordinate systems (the scene's and its images') MUST be connected by transformations: there must be a path of one or more transformations between any two of them (they don't all need to link to each other directly).
  • A transformation's parameters MUST fit the coordinate systems it links (e.g. a translation between two 2D coordinate systems has 2 values).

Which coordinate system is the 'main' one?

If a viewer picks a default coordinate system to display a scene in, the spec RECOMMENDS the first of the scene's own coordinateSystems. Likewise, when writing a scene, if one coordinate system acts as the common reference for the others (like stage above), put it first.

Do I need scene coordinate systems at all?

A transformation may also link one image directly to another (both with a path), with no scene coordinate system in between. This is natural for registration, where you map a "moving" image onto a "fixed" one:

{
  "type": "affine",
  "affine": [[...], [...], [...]],  // a 3x4 matrix, for 3D images
  "input": {"path": "moving_image", "name": "physical"},
  "output": {"path": "fixed_image", "name": "physical"}
}
Where do large transformation parameters go?

Some transformations store their parameters in Zarr: an affine or rotation matrix can (instead of inline JSON), and the vector field of a displacements or coordinates transformation (e.g. for non-rigid registration) must, as a multiscale image group. In a scene, those SHOULD be stored in a group called coordinateTransformations, next to the images.
